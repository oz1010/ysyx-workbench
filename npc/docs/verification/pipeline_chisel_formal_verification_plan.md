# pipeline-chisel 逐指令状态切换差分验证方案

## 1. 验证目标

验证对象为 `vsrc/core/pipeline-chisel/riscv32e_core.v`（DUT），参考模型为 `vsrc/core/single/riscv32e_core_sc.v`（REF）。

核心思路：生成一组合法指令序列，默认长度 `N=5`，将同一序列按顺序提供给 REF 和 DUT；分别采集每条指令引起的外部可观察状态切换事件，最后按指令顺序比较记录。REF 为单周期核，理想情况下 N 条指令在 N 个执行周期内完成采集；DUT 因流水线、反压和访存等待，可以经过不同数量的时钟周期。比较不要求逐周期同步，只要求每条指令对应的状态变化一致。

主要比较对象：

1. **MEM 事务**：读写请求的地址、操作类型、有效写数据，以及与请求对应的响应/完成事件。
2. **GPR 写入**：有效写使能、目的寄存器和写入数据；写 x0 不作为有效寄存器状态变化，但可按接口契约额外检查。
3. **Trap/CSR 写入**：Trap 事件及有效字段；CSR 写使能、地址和数据。两者的语义和有效条件需分别定义。
4. **退休指令**：退休事件及其对应指令身份/顺序。若接口不直接导出退休指令，需要由 IF 接收序号和退休顺序建立关联，不能仅凭周期或 PC 猜测。

本方案比较的是每条指令的**状态切换事件记录**，不是只比较执行结束后的最终寄存器快照。

## 2. 总体架构

```text
                指令序列 seq[0..N-1]，默认 N=5
                       /             \
                      v               v
             REF 指令输入          DUT IF 输入
             单周期执行             req/rsp 握手
                      |               |
              按指令采集事件     按事件使能采集事件
                      |               |
                REF 事件队列      DUT 事件队列
                       \             /
                        v           v
                    按序号/顺序逐条比较
```

建议将验证环境拆分为以下职责：

- `pipelinetest.sv`：REF、DUT 实例与顶层连接。
- `instruction_sequence.sv`：生成或约束长度为 N 的合法指令序列，并给每条输入指令分配验证序号。
- `ref_monitor.sv`：采集 REF 每条指令对应的状态变化。
- `dut_monitor.sv`：依据接口握手、使能和退休事件采集 DUT 状态变化。
- `event_scoreboard.sv`：保存两侧记录，按顺序匹配并比较。
- `formal_env.sv`：IF/MEM 响应模型、符号内存、复位和环境约束。
- `verify.sby` / `Makefile`：形式化任务、深度、solver 和构建配置。

文件可以合并，但指令生成、事件采集、事件关联和比较的职责应保持清晰。

## 3. 指令序列输入与 PC 处理

### 3.1 指令序列

指令序列长度参数化：

```systemverilog
parameter int N = 5;
logic [31:0] instr_seq [0:N-1];
```

指令序列应由独立约束定义为合法指令，而不是根据 DUT 输出选择指令。序列中的寄存器编号、opcode/funct、立即数、访存大小和地址对齐等约束应明确记录。首版可先覆盖直线执行的整数 ALU 指令，再增加访存、控制流和 Trap/CSR 指令类别。

REF 与 DUT 必须接收相同的指令内容和相同的逻辑顺序。建议给每个输入槽分配仅用于验证环境的 `seq_id`，用于追踪指令被接受、被冲刷以及最终退休的关系；该 ID 不要求成为 DUT 生产接口的一部分。

### 3.2 IF 接口

IF 接口用于输入指定指令序列。验证比较不使用 PC 数值作为两核的匹配键；PC 不参与逐条事件匹配。

- REF 按序列槽依次执行 `instr_seq[i]`。
- DUT 通过 IF 请求/响应接口获得对应指令；响应必须与已接受请求的地址/序号正确关联，不能在响应时直接读取“当前 PC”来替代请求时的指令。
- DUT 的 PC/dnpc 可作为可选的独立性质检查，但不作为 REF/DUT 事件记录的配对依据。
- 不能把“忽略 PC 比较”解释为允许 DUT 的 IF 请求与输入序列错配。

### 3.3 控制流限制

如果直接将指令序列按槽顺序无条件送入流水线，分支/JAL/JALR 可能冲刷流水线中已接收的年轻指令。因此必须明确验证模式：

- **基础序列模式**：先限制为不改变控制流的指令，验证 ALU、GPR 和基本访存事件。
- **控制流模式**：输入序列定义为可被取指的程序流，并显式建模 redirect、flush、已接受但被取消的指令和重取指。被 flush 的指令不能记为退休指令；不能将其副作用当成有效指令的状态切换。
- 不得通过假设所有已接收指令都必然退休，或忽略错误路径副作用来简化控制流验证。

## 4. 状态切换事件记录

两侧采用统一的逻辑记录格式，但允许各事件在不同周期出现。每条指令的记录至少包含：

```text
InstructionRecord {
    seq_id,
    retired,
    mem_events[],
    gpr_write_events[],
    csr_write_events[],
    trap_events[]
}
```

如果实现阶段暂不支持某类事件，可将该类标记为本任务不覆盖，并断言该任务中不会出现该类事件；不能静默丢弃事件。

### 4.1 MEM 事件

每个 MEM 请求在 `req_valid && req_ready` 时记录请求事件，保存地址、op、有效写数据及请求序号。响应在 `rsp_valid && rsp_ready` 时记录完成事件。对 load，还要记录环境实际提供的原始读数据/架构读值，以便区分请求错误、响应错误和 load 扩展错误。

MEM 比较至少检查：

- 读写方向和访问宽度；
- 完整字节地址；
- store 的有效写数据位；
- 请求与响应一一对应，不能缺失、重复或错序；
- 每条退休指令预期的访存事件数与实际事件数一致。

MEM 请求通常可能早于对应指令退休，因此不能简单把“本周期的 MEM 请求”附加到“本周期退休的指令”。应通过有序事务队列、已接受指令的 `seq_id` 关联；如果 DUT 外部接口没有事务 ID，则在明确的 in-order 单 outstanding 契约下用请求顺序关联，并把这一限制写入验证边界。若无法可靠判定某条请求属于哪条指令，需补充可观察关联机制或将该场景标记为尚不可验证。

首版可先使用单 outstanding 的 IF/MEM 环境。服务端必须在请求握手时锁存地址、op 和数据；响应延迟期间保持 payload 稳定。store 也要提供完成响应。

### 4.2 GPR 写入事件

在接口定义的有效 GPR 写事件发生时记录：

```text
{ seq_id, wen, waddr, wdata }
```

只对 `wen && waddr != 0` 的事件比较目的寄存器与数据。另行断言写 x0 不改变可观察的 x0 状态。每条退休指令的预期 GPR 写事件由 REF 独立执行结果得到；不应从 DUT 的写回结果构造 REF 期望值。

### 4.3 Trap/CSR 写入事件

Trap 和普通 CSR 写入分别记录，避免把异常状态更新误当成普通 CSR 指令写入：

- CSR：`{seq_id, csr_wen, csr_waddr, csr_wdata}`。
- Trap：`{seq_id, trap_en, epc, cause, tval, status}`，只比较接口契约规定为有效的字段。

必须先定义 CSR 写事件语义，例如“写相同值”是否仍算一次写事件；也必须明确 Trap 字段在什么条件下有效。若两核复位 CSR 初态不同，CSR/Trap 任务应先建立合法且可比较的初态，不能通过假设内部状态相等来绕过。

### 4.4 退休事件

以 `inst_done` 或正式定义的退休有效信号采集退休事件。连续周期有效表示连续退休，不能只检测上升沿。

每个退休事件应恰好消费一个尚未退休且未被 flush 的指令序号。比较两侧的退休条数、退休顺序和每条指令的事件记录。若正式接口不导出退休指令本身，应依据按序接受的指令队列关联；仅比较 GPR 写事件不足以证明所有指令均退休，因为有些指令没有 GPR 写回。

## 5. REF 与 DUT 的采集时序

### 5.1 REF

REF 按 `instr_seq[0]` 至 `instr_seq[N-1]` 顺序执行。对于不访存、不产生 Trap/CSR 复杂交互的单周期指令，预期每条指令一个执行周期，采集其当周期有效状态变化，并在沿前采样、沿后更新记录队列。

访存指令需保证 REF 所需响应在其执行采样点可用，或明确建模 REF 的接口适配方式。不能默认所有带 MEM 的指令仍然可以在没有响应数据的情况下正确地一个周期完成。

### 5.2 DUT

DUT 允许经历任意符合环境边界的流水线周期数。采集条件按各类接口的真实事件定义：

- IF：`if_req_valid && if_req_ready` 记录指令请求被接受；响应握手记录对应指令数据返回。
- MEM：`mem_req_valid && mem_req_ready` 记录事务被接受；响应握手记录完成。
- GPR/CSR/Trap：依据各自正式写使能采集事件。
- 退休：依据 `inst_done` / retire-valid 采集，不能用 IF 接收或某级 `en` 替代退休。
- 级间 `valid && ready`、`en` 可用于解释流水线推进和定位停顿，但除非该信号属于稳定、正式的验证接口，否则不要将内部信号作为架构正确性的唯一依据。

采样应统一在同一时钟沿的更新前状态，避免部分字段来自沿前、部分字段来自沿后。所有记录均附带验证序号或通过有序队列关联。

### 5.3 收集完成条件

不能仅等待固定 N 个周期。REF 与 DUT 分别维护完成计数：

- 已接受/执行指令数；
- 已退休指令数；
- 已完成 MEM 事务数；
- 当前 outstanding 请求数；
- 未匹配事件队列长度。

在 `N` 条目标指令均按预期退休，且 MEM outstanding 与事件队列已按该任务规则排空后，才进行完整记录比较并结束任务。若超时，报告为进展失败/超时，而不是把尚未产生的事件当作相等。

## 6. 按指令顺序比较

比较器维护 `ref_record[i]` 与 `dut_record[i]`，对 `i=0..N-1` 逐条比较：

1. 两侧均存在且只存在一次对应退休事件。
2. MEM 事件的数量、顺序、方向、地址、op、有效写数据和响应关联一致。
3. GPR 有效写事件的数量、顺序、目的寄存器和数据一致。
4. CSR 写事件的数量、顺序、地址和数据一致。
5. Trap 事件的数量、顺序及有效字段一致。
6. 不允许记录之外的额外副作用；特别检查 flush 指令、重复请求、未退休 store 和任务结束时残留事务。

若一条指令可产生多个外部事件，应按该指令内部的事件顺序比较。不能只对各类事件分别比较总数，因为两条指令之间的事件互换可能在总数相同的情况下仍是错误。

PC 值不参与配对比较，但可作为诊断字段保留；如需验证跳转目标或架构 PC 正确性，应另设独立性质，不与本方案的顺序配对混为一谈。

## 7. 形式化约束与性质

### 7.1 允许的环境假设

- 复位序列与统一的初始条件；
- 指令序列长度及独立定义的合法指令约束；
- 环境自身的 ready/响应延迟范围；
- 符号初始内存及本任务声明的地址/对齐范围；
- 首版固定中断输入，后续再扩展中断。

### 7.2 必须断言的性质

- DUT 的 IF/MEM 请求合法，反压期间请求 payload 稳定；
- 已接受的请求最终按环境协议得到匹配响应；
- 每条指令的退休事件最多一次，且退休顺序符合输入程序流及 flush 规则；
- GPR/CSR/Trap 写事件只在接口契约允许的时刻发生；
- MEM 请求、响应和退休关联无重复、遗漏、错序；
- 不存在未被 REF 期望记录解释的副作用；
- N 条指令完成后，所有要求排空的 outstanding 与日志为空；
- 两侧逐指令事件记录完全一致。

禁止假设 DUT 输出等于 REF 结果，禁止假设 DUT 的请求/写回正确，也不能把没有退休或没有事件的空轨迹当作有效 PASS。

### 7.3 覆盖与负向自检

至少覆盖：N 条指令全部退休、连续退休、流水线停顿、IF/MEM 反压、GPR RAW 依赖、连续写同一寄存器、各类 load/store、响应等待、控制流 flush 与旧响应重叠（控制流任务）。

在专门的负向测试配置中扰动 GPR 写地址/数据、MEM 地址/op/写数据、Trap 字段、退休有效信号或插入重复/缺失事务，要求相应比较性质失败，以证明监视器确实观察了这些字段。

## 8. 实施阶段

1. **阶段 A：直线 ALU 指令**。默认 N=5；不含访存和控制流，验证指令顺序、退休与 GPR 写事件。
2. **阶段 B：MEM 事件**。增加 load/store、响应模型、事务日志和有效写数据比较。
3. **阶段 C：依赖与停顿**。加入 RAW、反压、不同响应延迟和连续退休。
4. **阶段 D：控制流**。明确 redirect/flush、已接受但被取消的指令和重取指规则。
5. **阶段 E：CSR/Trap**。统一可比较初态，分别比较普通 CSR 写与 Trap 状态更新。
6. **阶段 F：可复现验收**。记录源文件摘要、工具版本、任务参数、BMC 深度、cover 结果和负向自检结果。

每阶段都应分别报告安全性质、cover 可达性和有界进展。Cover 命中不代表正确性证明；有限深度 BMC 的结论仅覆盖指定指令集合、环境协议和展开深度。

## 9. 关键设计边界

- **不按 PC 匹配，不等于不检查指令身份。** 必须用输入序号和退休顺序关联，PC 可只作为诊断或独立性质。
- **输入顺序必须考虑 flush。** 对控制流指令，不能简单假设所有已送入 DUT 的指令都将退休。
- **事件必须有归属。** MEM 请求可能早于退休，必须使用事务日志/指令队列关联；无法可靠关联时不能宣称逐指令 MEM 差分已完成。
- **状态事件与最终状态不同。** 最终 GPR 一致不能代替对 MEM、GPR 写、CSR/Trap 和退休事件的检查。
- **有限序列验证不等于全 ISA 证明。** 默认 N=5 是可配置的验证窗口，结论受指令约束、响应环境、内存模型与 BMC 深度限制。
